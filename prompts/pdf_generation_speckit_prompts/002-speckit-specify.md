# 002 — /speckit.specify

```markdown
/speckit.specify

Feature name:
PDF Generation Engine Stability and Layout Correctness

Problem:
The library has a broad PDF generation surface that includes document builders, report composers, grids, summaries, headers, footers, images, QR/barcodes, templates, export services, preview, printing, and sharing.

The goal of this feature is to audit, test, and fix defects related only to the PDF file generation process and document construction mechanics.

Out of scope:
- Do not verify correctness of user-provided data.
- Do not validate business calculations.
- Do not check financial totals, tax values, accounting logic, voucher semantics, or report data accuracy.
- Do not rewrite templates for business correctness.
- Do not redesign the visual identity unless required to fix PDF layout failure.
- Do not add unrelated features.

In scope:

1. PDF document creation lifecycle
   - PdfDocument initialization
   - page settings
   - page size
   - orientation
   - margins
   - compression
   - save/generate/dispose behavior

2. Page state management
   - current page reference
   - current page index
   - page count
   - currentY
   - layout result
   - state after newPage()
   - state after generate()
   - state after multi-page drawing operations

3. Layout overflow and page-break behavior
   - text overflow
   - rich text overflow
   - info box overflow
   - summary overflow
   - report header overflow
   - bullet list overflow
   - section divider overflow
   - large spacing overflow
   - large image overflow
   - multiple components near page bottom

4. Header/footer safety
   - header reserved height
   - footer reserved height
   - content must not overlap header
   - content must not overlap footer
   - new pages must respect header/footer
   - report composer must apply header/footer before content actions

5. Multi-page grid and component synchronization
   - if a grid or any component creates continuation pages, the builder must update its current page and currentY using the final PdfLayoutResult page and bounds.
   - summary after a multi-page grid must appear on the correct page, below the grid, not on the previous page or behind the footer.

6. RTL/LTR PDF generation mechanics
   - text direction must be applied consistently.
   - start/end alignment must respect RTL/LTR.
   - mixed bilingual layouts must not overlap due to direction mistakes.
   - this is layout correctness only, not language/content validation.

7. Image and QR/barcode generation safety
   - images must fit within content bounds or be scaled safely.
   - image attachments must not overflow beyond page boundaries.
   - full-page image pages must respect header/footer and margins.
   - QR/barcode drawing failures must be handled without corrupting the PDF.

8. File generation and result handling
   - generated bytes must be non-empty and openable.
   - errors must return clear failure results where service APIs use result models.
   - generation manager jobs must not swallow exceptions silently.
   - batch generation must report per-job failures correctly.

9. Export/save integration
   - PDF bytes must be saved/exported consistently.
   - export failures must be surfaced clearly.
   - do not validate content data during export.

Primary files to inspect:
- lib/src/builders/pdf_document_builder.dart
- lib/src/services/pdf_generation_manager.dart
- lib/src/services/pdf_service.dart
- lib/src/services/export/pdf_export_service.dart
- lib/src/services/export/batch_exporter.dart
- lib/src/components/widgets/pdf_data_grid.dart
- lib/src/components/widgets/pdf_summary.dart
- lib/src/components/widgets/pdf_info_box.dart
- lib/src/components/widgets/pdf_report_header.dart
- lib/src/components/widgets/pdf_rich_text.dart
- lib/src/components/widgets/pdf_barcode.dart
- lib/src/components/widgets/pdf_watermark.dart
- lib/src/templates/**
- example/lib/documents/**

Acceptance criteria:
1. PDF generation never produces empty bytes for successful generation.
2. Generated PDFs are structurally valid and openable.
3. Content does not overlap headers or footers.
4. Text and components near the bottom of a page either fit or move to a new page.
5. New pages start below the reserved header area.
6. Remaining height always accounts for footer space.
7. Multi-page grids update the builder state to the final rendered page.
8. A summary after a multi-page grid appears after the grid on the correct page.
9. Images are scaled or rejected with a clear error when they cannot fit safely.
10. QR/barcode rendering failure does not corrupt the entire PDF unless the component is required.
11. ReportComposer applies header/footer before queued content actions.
12. Batch PDF generation reports partial failures without hiding them.
13. Tests cover LTR and RTL configurations.
14. Tests cover portrait and landscape page orientations.
15. Tests cover small page sizes or constrained margins to force page breaks.
16. README.md and CHANGELOG.md are updated only for real API or behavior changes.
```
