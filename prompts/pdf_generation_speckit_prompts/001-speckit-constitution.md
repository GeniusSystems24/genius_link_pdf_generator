# 001 — /speckit.constitution

```markdown
/speckit.constitution

This project is a Flutter/Dart PDF generation library.

Core engineering principles for this feature:

1. PDF Generation Correctness First
   The primary goal is to make generated PDF files structurally valid, openable, printable, exportable, and stable across supported layouts.

2. Scope Boundary
   This work must focus only on PDF generation mechanics:
   - page creation
   - page breaks
   - layout bounds
   - header/footer reserved space
   - currentY tracking
   - multi-page components
   - image scaling
   - grid pagination
   - summary placement
   - RTL/LTR layout behavior
   - file byte generation
   - export/save failure handling

   Templates and their supporting files must be separated under `lib/templates`.
   `lib/src` must remain reserved for the core document-generation library components only.

   Do not validate, correct, or reinterpret user-provided business data.
   Do not check whether financial totals, tax values, voucher amounts, or report data are semantically correct.
   User-provided content is outside this feature scope.

3. Builder State Integrity
   The PDF builder must keep page state, current page index, current page reference, currentY, layout result, header space, and footer space synchronized after every drawing operation.

4. Header/Footer Safety
   No content may overlap header or footer templates.
   All new pages must start below the reserved header area and stop before the reserved footer area.

5. Multi-page Component Safety
   Any component that can create or continue on new pages must return enough layout information for the builder to update the current page and Y position correctly.

6. Deterministic PDF Output
   PDF generation should be deterministic for the same input, configuration, fonts, page size, orientation, and layout options.

7. Fail Fast With Clear Errors
   Invalid generation states should fail with descriptive errors instead of silently producing corrupted, clipped, empty, or partially generated PDFs.

8. Test Before Fix
   Add focused tests that reproduce layout and generation defects before changing implementation.

9. Minimal Public API Breakage
   Preserve existing public APIs unless a breaking change is absolutely required.
   If a breaking change is required, document it clearly in README.md and CHANGELOG.md.

10. Documentation Discipline
   Update README.md and CHANGELOG.md only for behavior, API, or migration-relevant changes.
   Any library modification or addition must also update the relevant `example/` usage so examples stay aligned with the current package behavior and public surface.

11. Regression Protection
   Any previously fixed PDF layout behavior must be covered by regression tests before related code is changed again.

12. Resource Safety
   PDF documents, image resources, fonts, and generated bytes must be handled safely without memory leaks, double-dispose issues, or invalid access after dispose.

13. Platform Awareness
   Fixes must not assume a single target platform. Generation should remain safe across mobile, desktop, web where supported by the current library.

14. No Silent Layout Corruption
   If a component cannot fit, split, scale, or move safely, it must fail clearly instead of silently drawing outside page bounds.

Governance:
- These principles apply to all subsequent spec, plan, task, analysis, and implementation steps.
- If implementation conflicts with these principles, stop and update the spec or plan before coding.
- Business-data validation is explicitly prohibited for this feature unless a separate feature is created for it.
```
