# 003 — /speckit.clarify

```markdown
/speckit.clarify

Clarify only ambiguities related to PDF generation mechanics.

Do not ask questions about:
- whether financial values are correct
- whether tax calculations are correct
- whether voucher amounts are correct
- whether user-entered data is semantically valid
- whether accounting entries are balanced
- whether report numbers are meaningful

Focus clarification on:

1. Platform priority
   Which platforms must be tested first?
   - Android
   - iOS
   - Windows
   - macOS
   - Web

2. Output path priority
   Which output path is most important?
   - raw PDF bytes
   - save to file
   - preview
   - print
   - share
   - export

3. Failure type
   Which failures are currently observed?
   - exceptions
   - blank PDF
   - empty bytes
   - clipped content
   - overlapping content
   - wrong page count
   - corrupted PDF
   - wrong RTL/LTR positioning
   - summary appears on wrong page
   - image overflows page
   - grid continues but builder state is wrong

4. Highest-risk documents
   Which document categories fail most often?
   - vouchers
   - invoices
   - reports
   - grids
   - summaries
   - image attachments
   - QR/barcodes
   - watermarks
   - template engine documents

5. Oversized component policy
   When a component is too large for the remaining space, what should happen?
   - move to next page
   - split across pages when supported
   - auto-scale
   - throw a clear error
   - use component-specific behavior

6. addSpace behavior
   Should addSpace() create a new page when space is not enough, or should it remain a low-level manual positioning method?

7. Absolute positioning behavior
   Should methods like addTextAt() be allowed to overlap by design, or should optional bounds validation be added?

8. Compatibility
   What is the minimum supported Flutter, Dart, and Syncfusion version for this fix?

9. Testing level
   Should tests inspect generated bytes only, or also inspect:
   - page count
   - currentY
   - layout result
   - final current page
   - openability of PDF bytes

10. API compatibility
   Should all public APIs be preserved even if some current methods behave inconsistently?

Default assumptions if no answer is provided:
- preserve public APIs
- add tests first
- fix generation defects without changing business template semantics
- prefer safe page breaks over clipping
- surface clear failures instead of silently producing broken PDFs
- do not add business-data validation
- do not rewrite all templates
```
