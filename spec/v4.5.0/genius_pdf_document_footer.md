# `GeniusPdfDocumentFooter`

Create a reusable and highly customizable PDF component named `GeniusPdfDocumentFooter`.

The component represents information displayed near the bottom of PDF pages.

It must be generic and reusable across invoices, reports, statements, vouchers, receipts, and other business documents.

## Supported content

Support optional footer information such as:

- Page number
- Total page count
- Generated by / user name
- Issue date
- Issue time
- Document serial number
- Document reference
- Additional custom metadata

Examples:

```text
Page 1 of 5
```

```text
Generated by: Ahmed
```

```text
Issued: 2026-09-07 10:30
```

```text
Document No: INV-000123
```

Every field must be optional.

Missing values must not leave unnecessary gaps or empty placeholders.

## Footer layout

Allow the consumer to determine which values appear and their order.

Support logical footer areas such as:

- `start`
- `center`
- `end`

Use direction-aware positioning.

For LTR:

- `start` → left
- `center` → center
- `end` → right

For RTL:

- `start` → right
- `center` → center
- `end` → left

Do not hardcode left/right behavior when logical start/end behavior is more appropriate.

## Page-number support

The footer must integrate correctly with multi-page PDF generation.

Page-number related values should support:

- Current page number
- Total page count
- Page-number formatting

The caller should not need to manually calculate these values outside the PDF generation process.

## Styling

Allow customization of:

- Typography
- Padding
- Spacing
- Alignment
- Separators
- Borders
- Background
- Start/center/end sections

Support RTL and LTR layouts.

## API and architecture requirements

- The public component name must be `GeniusPdfDocumentFooter`.
- Keep required parameters to the minimum actually necessary.
- Prefer optional parameters with sensible defaults.
- Do not reserve empty space for absent metadata.
- Avoid hardcoded labels where localization should be used.
- Support localization.
- Keep the API generic and independent of a specific document type.
- Separate footer data, formatting, styling, page-number logic, and rendering concerns where appropriate.
- Follow the existing PDF architecture and coding conventions of the project.
- Add Flutter/Dart documentation comments for all public classes, constructors, fields, enums, and important methods according to Flutter documentation conventions.

The exact API may be improved if a cleaner design is possible.
